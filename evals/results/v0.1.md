# slimproof eval v0.1

**Question:** slimproof makes tool descriptions shorter. After that, does Claude still select the correct tool with the correct arguments?

**Answer:** yes, for the 6 servers in this eval.
- **Slim vs original:** the slim tools got the same scores as the original tools, within one request per server. Both Claude Haiku 5.5 and Claude Sonnet 5.5 show this.
- **Tokens:** the slim tools use 16% fewer prompt tokens in total, and 54% fewer for Desktop Commander.
- **Strip-all:** we also tested tools with all descriptions removed. This saves more tokens, but the model then makes argument errors that the slim tools do not cause.

## Overall results

These results include all 6 servers, with 180 requests for each variant.
- **Haiku:** the mean of 3 runs. When the runs give different scores, the range is in brackets.
- **Sonnet:** 1 run.

| Model | Variant | Prompt tokens | Tool acc. | Arg valid | False calls |
|---|---|---|---|---|---|
| Haiku 5.5 | original | 93,579 | 99% (98%-99%) | 98% (98%-99%) | 0% |
| Haiku 5.5 | **slim** | **78,503 (-16%)** | 99% (98%-99%) | 99% (98%-99%) | 0% |
| Haiku 5.5 | strip-all | 56,157 (-40%) | 98% | 97% | 0% |
| Sonnet 5.5 | original | 93,579 | 99% | 99% | 0% |
| Sonnet 5.5 | **slim** | **78,503 (-16%)** | 99% | 99% | 0% |
| Sonnet 5.5 | strip-all | 56,157 (-40%) | 98% | 98% | 0% |

The columns mean:
- **Prompt tokens:** the total for the 6 servers, as the API counts them. Each total includes three parts:
  - the tool list
  - a short context for each server (less than 150 tokens)
  - the system prompt that the API adds for tool use

  The API measures this number. It is not an estimate.
- **Tool acc.:** the first tool call is the expected tool. For a request that needs no tool, no tool call is correct.
- **Arg valid:** the correct tool, arguments that match the tool's JSON schema, and the values the request gives (for example, the file path). We count this only for requests that need a tool.
- **False calls:** the model calls a tool for a request that needs no tool. Each variant has 18 of these requests.

## Findings

1. **The slim tools kept the accuracy on all servers.** The largest difference from the original is one request:
   - It happened on Notion with Haiku.
   - The slim variant read the page before a find-and-replace edit, in all 3 runs. The original variant did the edit immediately.
   - With Haiku, the slim tools got slightly higher scores than the original tools on Desktop Commander and Filesystem.
2. **Without descriptions, the model makes argument errors but still selects the correct tool.** Strip-all selected the correct tool in almost all requests, because the tool and parameter names have much meaning. Its errors come from details that only a description gives, and they occur again in each run:
   - **Filesystem `search_files`:** for "all Python files anywhere", the model uses `*.py`. This pattern finds only files in the top folder. The description that explains `**/*.py` is not there. Both models made this error.
   - **Chrome DevTools `navigate_page`:** the model adds an `includeSnapshot` parameter. This tool does not have that parameter, so the call fails the schema check. Haiku did this in 3 of 3 runs.
   - **Desktop Commander:** the model reads the full configuration before it sets a value. Without the description, it does not know the key name `fileReadLineLimit`. Haiku did this in 3 of 3 runs.
3. **No variant made false calls.** For questions that need no tool, for example "What does the chmod command do?", the model answered without a tool call in all runs.
4. **The slim tools make each request less expensive.**
   - **Haiku:** the full run (3 runs, 540 requests for each variant) cost $0.149 with the original tools and $0.132 with the slim tools (-11%).
   - **Sonnet:** one run cost $0.783 and $0.703 (-10%).
   - The cost saving is a little smaller than the token saving, because the output tokens do not change.

## Method

- **Servers:**
  - We used 6 popular MCP servers that start without an account, at fixed versions ([`servers.json`](../servers.json)).
  - We saved the tool definitions as snapshots ([`snapshots/`](../snapshots/)). The snapshots keep only the fields that the Claude API receives: `name`, `description` and `inputSchema`.
- **Variants:**
  - **original:** the snapshot, as the server publishes it.
  - **slim:** we ran the slimproof `/slimproof` skill on each server ([`slim/`](../slim/)). The slimproof guard then checked each result. The guard makes sure that only descriptions changed, and that all names, types and enums are the same.
  - **strip-all:** the original, with all `description` fields removed from the tools and from all parameters.
- **Requests:**
  - There are 30 requests for each server, 180 in total ([`datasets/`](../datasets/)).
  - About 70% are easy requests. About 20% are confusable requests, where two tools are easy to mix up, for example `list_directory` and `directory_tree`. About 10% are questions that need no tool.
  - We checked each expected answer against the **original** tool definitions.
- **Context:**
  - Each server gets one short context. It is the same for all variants ([`context.json`](../datasets/context.json)).
  - The context gives the allowed folder, a page snapshot with element IDs, the current repository, or the Notion page IDs.
  - Without this context, the correct first step for the model is a search, not the task itself.
- **Models:** `claude-haiku-5-5` (3 runs) and `claude-sonnet-5-5` (1 run). Both use `effort: "medium"` and `tool_choice: auto`.
- **Scoring:** we score the first tool call in each response, with these rules:
  - Relative paths start from the folder in the context.
  - Lists can be in any order.
  - A JSON string counts as the object that it contains.
  - Some requests ask for two files. Two parallel single-file reads in one response count as correct, the same as one read of both files.
- **Code:**
  - The runner is [`run_eval.py`](../run_eval.py).
  - It saves each response in a cache. The cache key is a hash of the model, tools, context, request and run number.
  - A second run is free if no input changes.

## Limits

- **The scores are near 100%.**
  - This eval shows that slimming did not decrease accuracy on these servers.
  - But the requests are too easy to show small differences.
  - The next version will add more difficult confusable requests.
- **Each server has 30 requests,** so one error is about 3 points.
- **Sonnet ran only once,** so its results have no range.
- **We did a pilot run first.** It was one Haiku run. We examined each error, and then changed the words of 9 requests. In these requests, the cause of the error was the wording, not the descriptions. The git history of `datasets/` shows the changes.
  - **5 requests had an error in all variants.** The model looked before it did the task. For example, it read a file before it added a line, or it read a pull request before the merge. The new wording gives the fact that the model looked for, for example "the file already ends with a newline".
  - **4 requests had an error in one or two variants.** The wording was not clear:
    - Three requests had a file name without a folder, or confusing words. The models searched for the file, or they guessed a folder.
    - One request said "lines 100 to 104". This can mean a 0-based or a 1-based offset.

    We knew which variants had these errors when we changed the words. The new wording only makes the request clear. It does not point to a tool.
- **The context is not real.** The element IDs, repository names and Notion IDs are examples. The model does not see real tool results. We score only the first tool call.
- **We tested Claude models only.** Other models and agents can use descriptions differently.

## How to repeat this eval

You need an Anthropic API key. The cache is not in the repository, so a new run calls the API.
- **Our cost:** about $0.40 for Haiku (3 runs) and $2.10 for Sonnet (1 run).
- **API bill check:** the full v0.1 eval, with the pilot run, cost $2.48 on the API bill. This is the same as the cost that the runner calculates from the usage numbers.

```bash
git clone https://github.com/Rounak7721/slimproof && cd slimproof
uv sync --extra claude
export ANTHROPIC_API_KEY=...
uv run python evals/run_eval.py --runs 3
uv run python evals/run_eval.py --model claude-sonnet-5-5 --runs 1
```

The runner writes the results to `evals/results/<model>.md`.
